# Миграции структуры: от разработки до сервера

Как вести изменения структуры Битрикса (инфоблоки, свойства, hl-блоки, группы, настройки) файлами миграций, проверять их
локально и в CI и применять на боевом сервере. Основа — модуль [sprint.migration](https://github.com/andreyryabin/sprint.migration);
BitrixBox даёт для него консольную обёртку `bx migrate` и воспроизводимое окружение.

## Что лежит где

| Что | Где | В git проекта? |
|---|---|---|
| Файлы миграций | `local/php_interface/migrations/Version….php` | да |
| Обязательные модули проекта | `local/bx-modules.txt` | да |
| Код модуля `sprint.migration` | том `www` (`bitrix/modules/sprint.migration`), ставится `bx migrate install` | нет |

В git вашего проекта обычно лежит папка `local/` (код, шаблоны, миграции). Её содержимое BitrixBox подключает как есть.

## Ежедневная работа

```bash
bx migrate install                  # один раз на окружение
bx migrate add "каталог товаров"    # новая миграция → правите up() и down()
bx migrate up                       # применить (перед этим сам поставит обязательные модули и сделает снимок)
bx migrate status                   # применено / ждут применения / неизвестные
bx migrate down                     # откатить всё, или bx migrate down <версия>
bx migrate redo <версия>            # откатить и применить заново (удобно при отладке up/down)
```

Миграцию можно писать руками через помощники модуля (`$helper->Iblock()->saveIblock(...)`, `saveProperty`, `Hlblock()`,
`UserGroup()`, `Option()` и т. д.; они идемпотентны: `save*` создаёт или обновляет) или **сгенерировать из уже настроенного
в админке**: `bx migrate run IblockBuilder` (инфоблок, свойства), `HlblockBuilder`, `OptionBuilder`, `UserTypeEntitiesBuilder`
и другие. Конструкторы интерактивные: отвечайте на вопросы в терминале, множественный выбор — названия через пробел.
Полный список: `bx migrate help`, документация модуля — [вики](https://github.com/andreyryabin/sprint.migration/wiki).

Советы:
- Пишите `down()`, даже если откат кажется лишним: `bx migrate redo` и откат после неудачного `up` на нём держатся.
- Одна миграция — одно осмысленное изменение; описание пишите по делу (оно видно в `ls` и `status`).
- Используйте `save*` вместо `add*`: миграция переживёт повторный запуск и частично применённое состояние.

## Обязательные модули проекта

Миграции предполагают, что нужные модули установлены. Перечислите их в `local/bx-modules.txt`:

```text
# обязательные модули проекта
iblock
highloadblock
```

`bx migrate up` ставит недостающие перед применением (то же вручную — `bx modules sync`), а `bx clean` их не удаляет и не стирает
их файлы. Если миграции нужен модуль, которого нет на диске (его файлы удалены), `bx` скажет об этом: верните файлы обновлением
или снимком.

## Воспроизводимость: сайт с нуля только из миграций

Главная проверка здоровья: пустой Битрикс + список модулей + миграции = ваша структура.

```bash
bx setup --defaults --edition standard --install --clean   # пустой Битрикс
bx migrate install && bx migrate up                        # всё остальное — из миграций
```

Если здесь что-то падает, миграции зависят от состояния, которого нет в репозитории (ручные правки в админке, данные).
Лучше узнать об этом в CI, а не на боевом сервере: готовый workflow ниже.

## Проверка в CI вашего проекта

Шаблон: [`docs/templates/bitrixbox-migrations.yml`](templates/bitrixbox-migrations.yml). Скопируйте его в
`.github/workflows/` вашего проекта (там, где `local/` лежит в корне репозитория). Он ставит BitrixBox указанной версии,
поднимает пустой Битрикс, кладёт в него ваш `local/`, ставит модуль миграций и применяет все миграции, затем откатывает их
(`down`) и применяет снова: так проверяется и `up`, и `down`.

## Выкладка на боевой сервер

BitrixBox предназначен для локальной разработки, на боевом сервере его нет. Файлы миграций те же, поэтому на сервере:

1. Один раз поставьте модуль `sprint.migration` (Маркетплейс 1С-Битрикс или composer, как описано в
   [документации модуля](https://github.com/andreyryabin/sprint.migration)).
2. Выкладывайте код вашего проекта (с папкой `local/php_interface/migrations`) обычным способом.
3. На сервере примените миграции консолью модуля (путь зависит от того, куда поставлен модуль):

   ```bash
   php bitrix/modules/sprint.migration/tools/migrate.php up
   # если модуль лежит в local/modules:
   php local/modules/sprint.migration/tools/migrate.php up
   ```

4. Перед применением на боевом сделайте резервную копию штатными средствами (аналог `bx backup`) и прогоните миграции на
   копии боевой базы.

Версию модуля на сервере держите той же, что и локально (в BitrixBox она закреплена: `bx migrate install --version X`
ставит другую).

## Известные ограничения

- В `sprint.migration` 5.15.1 консольные конструкторы падали на вопросах с множественным выбором (`TypeError` из-за
  типа возвращаемого значения). `bx migrate install` исправляет это одной строкой в файле модуля; в новых версиях модуля
  исправление, возможно, не понадобится (команда сама это определит).
- В консоли отключены кеши инфоблоков (блок в `bitrix/php_interface/dbconn.php`, действует только для CLI): иначе тип
  инфоблока, созданный миграцией, не виден в том же процессе. На сервере для миграций это тоже может быть актуально: если
  создание инфоблока сразу после типа падает с «Неверный тип блока», разделите их на две миграции или добавьте такой же блок
  в `dbconn.php` сервера.
- Миграции переносят структуру, а не данные (товары, пользователи, заказы): для них нужны другие средства.
