# BitrixBox

[![CI](https://github.com/razzhivine/bitrixbox/actions/workflows/ci.yml/badge.svg)](https://github.com/razzhivine/bitrixbox/actions/workflows/ci.yml)
[![Матрица](https://github.com/razzhivine/bitrixbox/actions/workflows/matrix.yml/badge.svg)](https://github.com/razzhivine/bitrixbox/actions/workflows/matrix.yml)
[![Релиз](https://img.shields.io/github/v/release/razzhivine/bitrixbox)](https://github.com/razzhivine/bitrixbox/releases)
[![Лицензия: MIT](https://img.shields.io/github/license/razzhivine/bitrixbox)](LICENSE)

Локальный 1С-Битрикс в Docker с одной командой `bx`: ставит окружение (PHP, nginx, MySQL/MariaDB), включает HTTPS,
проходит мастер установки Битрикса без браузера, убирает демо-данные, делает снимки и откатывает их. Существующий сайт
переносится одной командой — из резервной копии Битрикса или прямо с сервера по SSH, с обезличиванием персональных данных.

> Неофициальный проект, не связан с 1С-Битрикс. Лицензия: [MIT](LICENSE). Версия: см. `bx version`, история — [CHANGELOG](CHANGELOG.md).

## Быстрый старт

```bash
./bx setup --defaults --edition standard --install --clean
```

Через полторы минуты: Битрикс «Стандарт» установлен, демо-данные и лишние модули убраны, сайт открыт по HTTP и HTTPS.
В конце команда выводит адрес админки, логин и **случайный пароль администратора: он показывается один раз, сохраните его**.
Пароли базы данных лежат в файле `.env`.

Чтобы писать `bx` из любой папки: `./bx install-cli`.

### Требования

- Docker (на macOS — Docker Desktop; `bx` сам его запустит) с Compose v2.
- `python3` — для команды `install` (мастер Битрикса без браузера).
- По желанию `mkcert` (`brew install mkcert`): тогда браузер доверяет HTTPS-сертификату, без предупреждений.
- Проверено (полный цикл: установка, очистка, диагностика, вход, откат): редакции «Старт», «Стандарт», «Малый бизнес» и «Бизнес»;
  MySQL 8.4 и 8.0, MariaDB 11.4 и 10.11; PHP 8.3 и 8.2; macOS и Linux (GitHub Actions). Битрикс этой версии требует PHP 8.2 и выше.

## Установка по шагам

| Что нужно | Команда |
|---|---|
| Всё с вопросами (редакция, БД, PHP, пароли, порты, HTTPS) | `./bx setup` |
| Всё без вопросов | `./bx setup --defaults --edition standard` |
| ...и сразу пройти мастер Битрикса | добавьте `--install` |
| ...и убрать демо-данные | добавьте `--clean` (работает только вместе с `--install`) |
| Мастер Битрикса отдельно, если окружение уже поднято | `./bx install` |
| Убрать демо-данные потом | `./bx clean` |

Если не использовать `--install`, мастер можно пройти в браузере по адресу из вывода `setup`
(сервер базы данных `db`, остальные данные в `.env`).

**Редакции.** `start`, `standard`, `small_business`, `business` скачиваются сразу архивом и ставятся мастером.
Редакцию `web` (bitrixsetup.php) автоматически не поставить: в ней редакцию выбирают в браузере.
Автоматический мастер проверен на всех четырёх; если у какой-то версии появится неизвестный шаг, драйвер остановится
и предложит продолжить в браузере. Windows/WSL не проверялся.

### Регистрация продукта

По умолчанию мастер проходится **без регистрации**, ваши данные никуда не отправляются. Чтобы зарегистрировать копию
(имя, фамилия и почта уходят на сервер 1С-Битрикс), укажите их явно; заглушки не подставляются:

```bash
./bx setup --defaults --edition standard --install --register \
  --reg-name Иван --reg-surname Петров --reg-email ivan@example.com
```

То же для отдельной команды: `./bx install --register --reg-name ... --reg-surname ... --reg-email ...`.

После регистрации Битрикс работает как пробная версия на 30 дней, а мастер сам ставит все доступные обновления
(на проверке: до версии 26.800.0). Без регистрации обновлений мастер не находит.

### Флаги `setup` и `init`

| Флаг | Значение |
|---|---|
| `--defaults` | без вопросов, всё по умолчанию (пароли случайные) |
| `--edition` | `web`, `start`, `standard`, `small_business`, `business` |
| `--db` | `mysql-8.4`, `mysql-8.0`, `mariadb-11.4`, `mariadb-10.11` |
| `--php` | `8.3`, `8.2` |
| `--project` | имя проекта Docker (префикс контейнеров и томов); по умолчанию имя папки |
| `--db-name` `--db-user` `--db-password` `--db-root-password` | параметры базы |
| `--http-port` `--https-port` `--db-port` `--mail-port` `--adminer-port` | порты на хосте (по умолчанию 8080, 8443, 3306, 8025, 8081) |
| `--https` `--no-https` `--redirect` | HTTPS и редирект с http на https |
| `--install` `--clean` | пройти мастер Битрикса / убрать демо-данные после него |
| `--admin-login` `--admin-password` `--admin-email` `--admin-name` `--admin-surname` | администратор (пароль по умолчанию случайный) |
| `--solution` | `corp_furniture` (по умолчанию) или `corp_services` |
| `--register` `--reg-name` `--reg-surname` `--reg-email` | регистрация продукта (см. выше) |
| `--skip-updates` | не ставить обновления в мастере (установка быстрее; потом `bx update`) |
| `--demo yes\|no` | с `no` Битрикс не копирует страницы сайта, и сайт остаётся недоустановленным; по умолчанию `yes` |

## Перенос существующего сайта

```bash
git clone https://github.com/razzhivine/bitrixbox.git shop && cd shop

./bx import ~/Downloads/shop.ru_20261008_full_ab12.tar.gz          # резервная копия из админки (части .1, .2 … подхватятся сами)
./bx import /путь/к/сайту --sql dump.sql.gz                         # файлы из папки и дамп базы
./bx import deploy@shop.ru:/home/bitrix/www --upload-proxy https://shop.ru --anonymize   # прямо с сервера по SSH
```

Команда сама создаёт окружение (если его ещё нет), переносит файлы и базу, переключает сайт на локальную базу,
кеш и сессии в файлах, выключает SMTP и secure-cookie, меняет адрес сайта на `localhost`, правила доступа по IP
«Проактивной защиты» и облачные хранилища переводит в безопасный режим, чистит очередь писем — и проверяет, что
главная и админка открываются. Папка `local/` попадает в ваш проект на диск. Боевой сервер не меняется: по SSH
только читаются файлы и делается дамп базы.

| Что нужно | Как |
|---|---|
| Не качать десятки гигабайт `upload/` | `--upload-proxy https://shop.ru` (или позже `bx upload-proxy https://shop.ru`): недостающие файлы nginx берёт с боевого сайта; `--save` — ещё и сохранять их локально |
| Не держать у себя персональные данные | `--anonymize` (или позже `bx anonymize`): почта, имена, телефоны, адреса и пароли пользователей, данные заказов, форм, подписок; задаётся пароль администратора и выводится один раз |
| Войти в админку | `--admin-password …` (без него — пароли боевого сайта) |
| Обновить копию позже | `bx pull` — свежая база с того же сервера; `--files` — и файлы (кроме `local/` и `upload/`), `--upload` — и `upload/` |
| Ключ или порт SSH | `ssh://user@host:2222/путь` и `--ssh-opts "-i ~/.ssh/deploy"`; работают и настройки из `~/.ssh/config` |

Перед заменой сайта и перед `pull` делается снимок: `bx restore` вернёт как было. Исходные настройки сайта (с боевыми
паролями) сохраняются в `backups/import-…/`, а не в корне сайта. Подробно — [docs/IMPORT.md](docs/IMPORT.md).

## Обновление

```bash
./bx update --check   # что доступно, ничего не меняя
./bx update           # спросит подтверждение, сделает снимок и поставит все обновления
./bx update --yes     # то же без вопроса
```

Работает так же, как «Обновление платформы» в админке: сначала обновляется сама система обновлений, потом модули по шагам.
Обновления получает только зарегистрированная копия (`--register` при установке); без регистрации сервер ничего не отдаёт.
Проверено: 94 обновления в 19 модулях (26.150.0 → 26.800.0) за 3,5 минуты. Если что-то пошло не так — `bx restore` вернёт
состояние до обновления.

## Миграции структуры

Изменения структуры сайта (инфоблоки, свойства, группы, настройки) удобно хранить в файлах миграций и применять на
любом окружении одной командой. `bx migrate` — консольная обёртка над модулем
[sprint.migration](https://github.com/andreyryabin/sprint.migration) (MIT); веб-интерфейс модуля не нужен.

```bash
./bx migrate install                 # поставить модуль (версия закреплена) и папку миграций
./bx migrate add "каталог товаров"   # создать файл local/php_interface/migrations/Version….php
./bx migrate ls --new                # что ещё не применено
./bx migrate status                  # применено / ждут применения / неизвестные
./bx migrate up                      # применить: обязательные модули → снимок → миграции
./bx migrate down                    # откатить (или down <версия>)
```

Файлы миграций лежат в `local/php_interface/migrations`, то есть на вашем диске и в git **вашего проекта**; сам модуль
это инструмент окружения и живёт в томе `www`. Остальные команды модуля (`redo`, `mark`, `delete`, `run`, `config`)
передаются как есть: `bx migrate run <конструктор>` задаёт вопросы прямо в терминале.

**Перед `up` автоматически делается снимок** (`bx backup`, метка `before-migrate`): если миграция что-то испортила,
`bx restore` вернёт состояние одной командой. Отключается флагом `--no-backup`.

**Обязательные модули проекта.** Миграция, создающая инфоблок, требует модуль `iblock`, а `bx setup --clean` оставляет
только четыре защищённых. Перечислите нужные модули в `local/bx-modules.txt` (по одному в строке, `#` — комментарий):
`bx clean` их не удалит (и не сотрёт их файлы), а `bx migrate up` предварительно поставит недостающие
(то же вручную: `bx modules sync`). Так сайт воспроизводится с нуля только из миграций:

```bash
./bx setup --defaults --edition standard --install --clean && ./bx migrate install && ./bx migrate up
```

Конструкторы (`bx migrate run IblockBuilder`, `HlblockBuilder`, `OptionBuilder` и др.) генерируют миграцию из уже
настроенного в админке: отвечайте на вопросы в терминале, множественный выбор — названия через пробел. В `sprint.migration`
5.15.1 они падали на таких вопросах (`TypeError`), `bx migrate install` исправляет это одной строкой в файле модуля.

Подробный гид: [docs/MIGRATIONS.md](docs/MIGRATIONS.md) (ежедневная работа, воспроизводимость с нуля, выкладка на сервер,
ограничения) и готовый workflow для CI вашего проекта: [docs/templates/bitrixbox-migrations.yml](docs/templates/bitrixbox-migrations.yml).

Про кеш: в консольных процессах `bx migrate install` отключает кеши инфоблоков (блок в `dbconn.php`, только `cli`):
без этого тип инфоблока, созданный миграцией, не виден в том же процессе, и создание инфоблока падает с «Неверный тип блока».

## Очистка демо-данных

```bash
./bx clean --dry-run   # только показать план
./bx clean             # интерактивно: спросит про модули, перед удалением сделает снимок
./bx clean --yes --all-modules --drop-tables --module-files   # то же без вопросов (это и делает setup --clean)
```

Удаляются инфоблоки (элементы, разделы, сами инфоблоки и их типы), все страницы и папки в корне сайта (остаются `bitrix`,
`local`, `upload`, `urlrewrite.php`, `.htaccess`), шаблоны кроме `.default`, демо-картинки, остатки удалённых модулей
(настройки, пользовательские поля, почтовые шаблоны, мастера) и по желанию файлы неустановленных модулей.
Модули удаляются штатными деинсталляторами; **`main`, `security`, `fileman`, `ui`, `sprint.migration` и модули из `local/bx-modules.txt` не удаляются никогда**.

Перед очисткой `clean` делает снимок (`bx backup`). Откат всего одной командой: `bx restore <снимок>`.

## Команды

| Команда | Что делает |
|---|---|
| `setup` | всё с нуля: Docker, окружение, HTTPS, по флагам мастер и очистка |
| `init` | настройка и запуск окружения |
| `install` | пройти мастер установки Битрикса без браузера |
| `import <источник>` | перенести существующий сайт: архив Битрикса, папка + `--sql`, `user@host:/путь` по SSH; `--anonymize`, `--upload-proxy`, `--admin-password` |
| `pull [--files] [--upload]` | обновить локальную копию с сервера (после `import` по SSH); перед этим делает снимок |
| `anonymize [--dry-run]` | обезличить персональные данные в локальной базе; перед этим делает снимок |
| `upload-proxy URL [--save]\|off` | недостающие файлы `upload/` брать с боевого сайта |
| `modules` | модули: `all`, `install <id…>`, `uninstall <id…>`, `required`, `sync` |
| `migrate` | миграции структуры (sprint.migration): `install`, `add`, `ls`, `status`, `up`, `down`, `run`, остальное как у модуля |
| `update` | обновить Битрикс до последней версии (`update --check` — только показать, что доступно); перед обновлением делает снимок |
| `clean` | очистка демо-данных, остатков и модулей |
| `https [--off]` | включить или выключить HTTPS (`--port`, `--domains`, `--redirect`, `--defaults`) |
| `passwords rotate` | сменить пароли БД (пользователь и root) везде: в базе, `.env` и настройках Битрикса; перед сменой делает снимок |
| `doctor` | диагностика: Docker, порты, сайт, HTTPS, кеш модулей, агенты, пароли, диск |
| `backup [метка]` | снимок: база, файлы сайта, `local`, `.env`; `backup list` — список |
| `restore [снимок]` | восстановить из снимка; текущее состояние сохраняется заранее (метка `pre-restore`) |
| `cron on\|off\|status` | агенты и почтовые события по расписанию (контейнер `cron`) или на хитах страниц |
| `cache-clear` | сбросить кеш Битрикса |
| `debug on\|off\|status` | подробные ошибки на странице и лог исключений |
| `sql` / `sql "запрос"` | консоль MySQL / выполнить запрос |
| `php ...` | PHP в контейнере, например `bx php -v` |
| `open site\|admin\|mail\|db` | открыть сайт, админку, почту или Adminer в браузере |
| `up` `down` `restart` `status` `logs` `shell` | управление контейнерами |
| `reset` | снести контейнеры, базу, файлы сайта и `.env` (спросит подтверждение) |
| `version` | версия BitrixBox (`bx --version`) |
| `install-cli` | сделать `bx` доступным из любой папки |

## Что внутри

- **php** (php-fpm), **nginx**, **db** (MySQL или MariaDB), **cron** (агенты Битрикса), **mailpit** и **adminer**.
- Файлы Битрикса лежат в томе Docker `www`, а не на диске: на macOS файловая система не различает регистр, и обновления
  Битрикса из-за этого теряют файлы. Ваш код кладите в `local/` — он лежит на диске и виден в IDE.
- **Почта.** Письма сайта наружу не уходят, а попадают в Mailpit: http://localhost:8025 (`bx open mail`).
- **База.** Adminer: http://localhost:8081, сервер `db` (`bx open db`).
- **Cron.** `bx cron on` переводит агенты и почтовые события на контейнер `cron` (раз в минуту); на хитах страниц Битрикс их
  больше не выполняет.

## Структура проекта

```
bx                      единственная команда-диспетчер
docker-compose.yml      сервисы (параметры из .env, имя проекта — BX_PROJECT)
docker/                 конфиги контейнеров: php/ (Dockerfile, php.ini, msmtprc), nginx/ (сайт, https, сертификаты)
scripts/                реализация команд: init.sh, https.sh, clean.sh, backup.sh, cron.sh, doctor.sh, passwords.sh, update.sh,
                        modules.sh, migrate.sh, import.sh, anonymize.sh, upload-proxy.sh, wizard.py;
                        protected-modules.txt — модули, которые не удаляются никогда
scripts/php/            PHP внутри контейнера: cleanup.php, modules.php, debug.php, cache.php, doctor.php, update.php, import.php, anonymize.php
scripts/remote/         то, что выполняется на сервере при import/pull по SSH (только чтение)
tests/                  сквозные проверки (e2e.sh, migrate.sh, import.sh) и тест мастера на записанном диалоге (test_wizard.py)
.github/workflows/      CI: проверка скриптов и сквозная установка с нуля
local/                  ваш код (шаблоны, php_interface, свои модули)
docs/                   гиды (docs/MIGRATIONS.md) и шаблоны CI для вашего проекта
backups/                снимки `bx backup` (в git не попадают)
```

## Безопасность

- Порты базы, Mailpit и Adminer открыты только на `127.0.0.1`, из локальной сети они не видны.
- Пароли базы по умолчанию случайные (24 символа), `.env` с правами 600, версии образов закреплены.
- Отладка (`bx debug on`) нужна только на время поиска ошибок; `bx doctor` напомнит её выключить.
- Мастер без `--register` ничего о вас на сервер 1С-Битрикс не отправляет.
- После `bx import` письма сайта не уходят наружу (Mailpit, SMTP Битрикса выключается), облачные хранилища — только на
  чтение; своя функция `custom_mail` в `init.php` не меняется — `import` о ней предупредит.

## Если что-то не так

Начните с `./bx doctor`: он проверяет Docker, порты, ответы сайта (в том числе что PHP выполняется, а не отдаётся как файл),
сертификат, кеш модулей, агенты и слабые пароли.

| Проблема | Что делать |
|---|---|
| Порт занят | поменяйте его в `.env` (`HTTP_PORT` и др.) и выполните `bx up` |
| Список модулей в админке не совпадает с базой | `bx cache-clear` (кеш списка модулей живёт сутки) |
| Нужно начать заново | `bx reset`, затем `bx setup ...` |
| Что-то сломалось после очистки или обновления | `bx backup list`, затем `bx restore <снимок>` |
| Слабый пароль БД (старая установка) | `bx passwords rotate` |
| Не помню пароль администратора | сбросьте в админке или через Adminer; при установке он выводится один раз |

## Ограничения

- Windows и WSL не проверялись (macOS и Linux — да).
- Режима «у меня есть лицензионный ключ» нет: доступна только регистрация по почте (`--register`).
- `bx update` в CI не проверяется (для обновлений нужна регистрация с настоящей почтой); проверен вручную.
- Пароль администратора мастер выводит один раз и нигде не сохраняет.
- Снимки (`bx backup`) занимают от сотен мегабайт (файлы сайта целиком) — удаляйте ненужные из `backups/`.
- Автоматический мастер зависит от устройства установщика 1С-Битрикс: после его обновления шаги могут измениться;
  CI раз в неделю прогоняет установку и сравнивает диалог с мастером с сохранённой записью (`tests/fixtures`) — видно,
  какие именно шаги или поля поменялись.
- `bx import`: зашифрованные резервные копии (`.enc`), сайты на PostgreSQL и многосайтовость с разными корнями не
  поддерживаются; сайты в кодировке windows-1251 переносятся, но BitrixBox рассчитан на UTF-8.
